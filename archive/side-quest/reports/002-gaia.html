One pipeline, three roles: who makes the judgment?

An engineer asks what broke and where, a team lead asks what keeps coming back, a manager asks what to fix first. SereneDB finds the evidence and computes every number; a judgment model reads it. We gave Jev and a fast LLM the identical evidence and the identical questions for all three roles, on two weeks of logs from a 10-service system with injected faults.

How to read this

Only held-out numbers say whether a result generalizes.

Lessons for teams building with Jev and SereneDB

Eight things we would tell a team starting tomorrow

  1. The evidence matters more than the model.

    The same LLM scored 0.38 on raw logs and 0.90 on SereneDB's evidence (held-out). Jev went from 0.34 to 0.80 on dev just by changing how the evidence was built, with the model and questions unchanged. Spend most of your effort on the SQL that selects and summarizes evidence.

  2. Compare a thing with its own past, not with everything.

    "This service logs this error 2× more than in its own last 24 hours" is what made the evidence work. Experiment 001 compared each job with all jobs and failed on new data.

  3. Jev reads literally; tell it only what changed.

    When the evidence listed routine ERROR lines with a note "seen in 211 of 219 windows", the LLM ignored them and Jev called them a fault. Filtering in code (show only new or ≥ 2× patterns) fixed most of this. Do the "is this unusual?" reasoning in SQL, then ask Jev the judgment.

  4. Let code decide the easy cases.

    73% of questions had no unusual pattern at all, so the answer "no fault visible" needs no model. A model call should be spent only where a judgment is actually needed.

  5. Numbers vs words did not matter.

    Jev is weak at math, so we tried removing raw counts and keeping only phrases like "about 2× its usual rate". Every Jev answer stayed the same. Precomputing ratios in SQL is still the right habit; it just was not the cause of the errors here.

  6. Jev is fast, cheap and consistent; the LLM is still more accurate.

    Held-out: Jev 0.85 vs LLM 0.90 macro-F1, but Jev answers in 237 ms vs 1.8 s, costs about 20× less, and never changed its answer across wordings or option orders. Pick by what your use case needs: high-volume triage favours Jev, one-off investigation favours the LLM.

  7. Missing telemetry cannot be fixed by a smarter model.

    In July only webservice1's logs exist. A database fault shows up there only as downstream errors, so both models named the wrong root service in the same cases (64%). Check what your logs can show before asking a model about it.

  8. Choose settings by cross-validation and freeze them before the final test.

    In 001 we picked settings from one dev score and the result collapsed on new data. Here we used 5 folds of whole days, kept the simpler option when the gain was within noise, and ran the held-out test once. The dev conclusions held.

Key terms · read once, refer back

What every label and number means

The setup

Jev
TypeSafe's judgment model. It does not write text; it picks from the options you give it and returns a probability for each option. Fast and cheap, but it does no math and reads input literally.
LLM (baseline)
gemini-3.8-flash, a fast general LLM, given exactly the same evidence and the same answer options as Jev, answering as a JSON form. This keeps the comparison fair.
SereneDB
The log database. It stores the logs, runs the SQL that finds the evidence, and computes every number the models see. No number comes from a model.
Window / question
One 15-minute slice of the whole system, e.g. "What went wrong between 11:56 and 12:11?". Each window is asked in 3 wordings, so 219 dev windows give 657 questions.
Template (pattern)
A log line with its variable parts removed, e.g. No such file or directory: <*>. Drain3 learns these from dev days only. Counting templates instead of raw lines makes "how often does this happen?" a simple SQL query.
Fault / no-trace / normal
Fault: an injected fault that shows in the logs (missing file, permission denied). No-trace: a memory fault that leaves no mark in the logs, so the right answer is "no fault visible". Normal: no injected fault.
Dev vs held-out
Dev (Aug 1–24) is what we tune on. Held-out (Aug 25–31 + all of July) is locked away: a guard script blocks anyone, including the AI assistant, from reading it. It is run once with the frozen settings, and only totals are printed.
Frozen
The setting chosen on dev and fixed before the held-out run. It is never changed after seeing held-out results.

Variants we compared

E0–E3 (evidence)
How the evidence is built. E0: 001-style, top patterns with how common they are overall. E1: each pattern compared with the same service's last 24 hours, only what is new or ≥ 2× usual. E2: E1 plus a per-service error table. E3: E2 plus example raw lines.
Q0, Q1, Q2, Q7 (question designs)
How we ask. Q0: pick the fault type and the key evidence item. Q1: adds an explicit "cannot tell from these logs" option. Q2: first "is there a fault?", then "which?". Q7: Q0 plus "which service is the root cause?", choosing from candidate services found by SQL.
L0–L2 (team lead)
L0: are these two incidents the same underlying problem? L1: classify each incident into a broad type, group in code. L2: is this a repeat of a known problem or new?
M0–M1 (manager)
M0: of two problems, which to fix first? M1: an impact score per problem, ranked in code. Scored against a rule written before the run (extra failed requests, × 2 if customer-facing).
Raw-logs LLM
The LLM given the window's raw WARN/ERROR lines plus its first and last 50 lines (up to 120k characters) instead of SereneDB's evidence. Shows what the evidence step is worth.
Classifier
Logistic regression trained on dev labels over per-service template counts (TF-IDF). Needs labelled data, which a real team usually does not have.
Keyword rules
Hand-written "if this text appears, it is this fault" rules. We wrote them after looking at the data, so they show a ceiling, not a fair baseline.

Metrics

Macro-F1 (higher is better)
The main accuracy score, 0 to 1. F1 per answer class (balance of "found the real cases" and "did not raise false alarms"), then averaged equally over classes. Unlike plain accuracy, a model cannot score high by always giving the most common answer.
95% CI
The range the true score likely falls in, from resampling the days 1,000 times. Wide ranges mean few examples. If two systems' ranges overlap a lot, the difference may be noise.
Brier score (lower is better)
How good the probabilities are, not only the answers. 0 = always right and certain; 2 = certain and wrong. A model that says 95% and is wrong is punished more than one that says 55% and is wrong.
Confidence
Computed from the model's probabilities, never self-reported: (p_max − 1/n)/(1 − 1/n), where p_max is the top option's probability and n the number of options. 0 = no preference, 1 = certain.
"Auto" answers, coverage
Answers above a confidence threshold get an "auto" badge; the rest go to a human. Coverage = share that gets the badge. "92% at 99.8% coverage" means almost all answers were auto and 92% of those were right.
Consistency checks
Same answer over 3 repeats, over shuffled option order, and over different wordings of the same question. A reliable tool should not change its mind for these.
Root service
Share of fault windows where the top-ranked root-cause service is the right one.
Fold SD, lean rule
Dev is split into 5 folds of whole days. A richer variant is kept only if it beats a simpler one by more than one standard deviation across folds; otherwise the simpler one wins.
p50, $ / 1k
Median response time per question, and cost per 1,000 questions.
R1–R6, C1–C3
Pass/fail criteria written in the plan before running. R = can the person act on the answer; C = Jev compared with the LLM.
How we got here · every decision, in order

From a failed held-out run to a three-role experiment

  1. Oct 11 · starting point

    Experiment 001 did not generalize

    On Hadoop, Jev tied the LLM on dev (0.51 vs 0.49 macro-F1) but dropped to 0.32 on held-out (LLM 0.42, raw-logs LLM 0.54, classifier 0.66). We listed ten reasons (plans/002-ideas.md). The biggest: held-out was all PageRank jobs while dev was mostly WordCount, the duration baseline ignored job type, and evidence settings were picked from one dev score.

  2. Oct 11 · data look

    What GAIA can and cannot answer

    We read only the injection records and the logs of Aug 1–5. Findings that shaped every later choice:

    • Only file-missing and permission-denied faults show up in the logs. Memory faults leave no trace (122 windows, volume and error rate unchanged). CPU bursts last 3 seconds. Login timeouts are per-request background.
    • Normal logs are noisy: about 4.5k ERROR lines a day per db/web instance.
    • Fault type is tied to service type, so naming the service in the question would leak the answer.

    Decisions: ask about the whole system in a time window; treat memory windows as a "no-trace" slice where the right answer is "no fault visible"; exclude CPU; keep login failures as background.

  3. Oct 11 · plan, then recalibration

    Calibrate to the brief: one pipeline, three roles (D13)

    The first draft compared Jev question designs. We recalibrated it to the challenge brief, so the plan was rewritten around the three roles. Engineer is the main, fully measured part; team lead and manager are smaller measured slices built on the engineer's incidents. Success criteria were rewritten to lead with "can the person act on it?" (R1–R6), with Jev vs LLM as comparisons (C1–C4). The manager has no true priority, so we pre-registered a proxy rule: extra failed requests × 2 if customer-facing, ties by affected minutes.

  4. Oct 11 · approved

    Branch from main after merging 001

    Plan approved with July in held-out and the impact rule as written. Branch exp/002-gaia-question-design created from the merged main.

  5. Oct 11 · amendment 1

    Held-out = the last week of August + all of July

    The plan said "stratified blocks from Aug 11–31". To fit Drain3 on dev days only in one streaming pass, held-out has to come last in time. The split became Aug 1–24 dev and Aug 25–31 plus July held-out: train on past weeks, test on the next week and on a month with only one service's logs. Stratification became a check that aborts if a fault type is missing.

  6. Oct 11 · amendment 2

    Cost cut: raw-logs baseline on one wording

    Estimated total ≈ $55–65 of LLM calls, half of it the raw-logs baseline. We chose to run that baseline on wording 0 only. Actual dev spend: Jev $0.32, LLM $18.32.

  7. Oct 11 · split run

    219 dev windows, 233 held-out windows

    Dev 35 fault, 69 no-trace, 115 normal (657 questions); held-out 58, 81, 94 (932). Pattern novelty turned out low: held-out adds only 4 templates, used by 2 of 1.1M WARN+ rows.

  8. Oct 11 · build

    Ingest and smoke test

    8.86M raw rows over OTLP in 94 s; 1.79M rollup rows via read_csv. A three-question smoke test on both models found one bug (SQL sums arriving as Decimal), fixed before the waves.

  9. Oct 11 · wave 1

    Evidence: E0 fails for Jev, E1 frozen

    E0 (001-style) gave Jev 0.34 and the LLM 0.99. The traces showed why: Jev read routine ERROR lines literally even when labelled "common: seen in 211 of 219 windows". E1 (per-service 24 h baseline, only what changed) gave 0.80 and 0.97. E2 scored a little higher, within one fold standard deviation, so the lean rule kept E1. Gate G1 passed: LLM on E1 0.98 vs raw logs 0.46. The keyword rules scored 1.00, and we flag that as unfair because the keywords came from the data look.

  10. Oct 11 · wave 2

    Question designs: Q7 frozen, Q1 just misses

    Q1 ("cannot tell") lifted Jev to 0.87 but the two-model average gain stayed below the pre-registered bar. Q2 (two-stage) was worse for both. Q7 (root-cause service from SQL candidates) found the right service 100% of the time for both models. Frozen engineer config: E1/Q7.

  11. Oct 11 · waves 3–4

    Lead and manager slices

    Same-problem F1 1.00 for both; repeat-or-new 0.93 vs 1.00. Manager agreement with the rule 94% vs 83%, order robustness 100% vs 89%.

  12. Oct 12 · held-out

    One run with the frozen config

    Run once on Aug 25–31 + July (932 questions) with E1/Q7 frozen from the dev result files. Jev 0.85, LLM 0.90, raw-logs LLM 0.38, classifier 0.67. Experiment closed (D14); held-out is not re-run.

  13. Oct 12 · post-hoc, dev only

    Numbers vs words: no difference

    We asked whether the raw counts in the evidence ("14 in this window, usually about 6") hurt Jev, which is weak at math. We removed them and kept only the computed phrase ("about 2x its usual rate"). Every Jev answer stayed the same; the LLM moved by one question either way. A follow-up look at the same runs showed where the gap really is: 73% of questions have no unusual pattern and need no model at all, and on the rest Jev calls almost any unusual routine error a fault (15 of 78 quiet windows right) while the LLM rejects most of them. Next design: code decides the easy cases and the citation; Jev gets one narrow per-item question, "real fault or routine behaviour?".

  14. Oct 12 · demo

    A field guide for teams new to Jev

    An interactive deck replays the recorded dev calls step by step, technique by technique, with this benchmark at the end: Jev Field Guide.

How it works · implementation

Where every number and every judgment comes from

The rule: SereneDB computes, Jev (or the LLM) judges, code assembles the answer. A question flows through four steps, called bricks.

flowchart LR
  Q["Question: what went wrong 11:56-12:11?"] --> P["1 Pattern (SQL): counts per service and template vs last 24 h"]
  P --> E["2 Evidence (code): keep new or 2x patterns, turn ratios into phrases"]
  E --> V["3 Verdict (Jev or LLM): pick fault type, key evidence, root service"]
  V --> F["4 Finding (code): answer + computed confidence + cited evidence"]

What we changed after 001

Five lessons from Hadoop, each built into the run

Compare a service with itself

Every pattern's count in the window against the same service's last 24 hours. 001 compared a job with all jobs.

Fixed history window

"New" and "more frequent" are relative to the previous 24 hours, never to the evaluation corpus.

Cross-service view

Per-service error tables and the earliest service to spike, so a downstream symptom is not mistaken for the cause.

Check against raw logs early

Gate G1: the LLM on our evidence must not lose to the LLM on raw logs. It won, 0.98 vs 0.46.

Choose by cross-validation

Five folds of whole days; a richer variant must beat a simpler one by more than one fold standard deviation.

The LLM is still a little more accurate; Jev is far faster and cheaper with nearly the same result.

Next

Experiment 002 is closed. Next: BGL

  • GAIA has only two log-visible fault types and four recurring problems, so the lead and manager judgments saturate. BGL (experiment 003) brings many alert categories and enough cases to measure calibration.
  • Jev's best lever was the explicit "cannot tell" option (+0.06 on dev). It missed the pre-registered bar here and gets tested again on BGL.
  • Jev's main weakness is literal reading of routine errors at about twice their usual rate. Candidates: a "routine noise" option with examples, or per-item judgments that can outvote one noisy line.
  • "Where" needs the root service's own logs. The July result shows what partial telemetry costs.
