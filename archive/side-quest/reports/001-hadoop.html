Jev × SereneDB · experiment 001 · Loghub Hadoop · dev split · Oct 9–11, 2026

Can a decision model explain why a job failed?

We built a small, fully traced pipeline that answers an engineer's question, "Why did Hadoop job X fail?", from logs alone. SereneDB finds and counts the evidence, Jev (TypeSafe's System One model) makes the judgment, and every claim can be followed back to SQL and raw log lines. This report covers every decision we made on the way, what worked, what didn't, and what changed because of it.

Cost per 1,000 questions$0.08LLM $1.37 · raw-logs LLM $6.01

We tuned on 105 dev questions and tested once on 80 held-out questions (20 jobs, including fault situations dev never had). Every variant ran on both Jev and a fast LLM with identical evidence, verified per question. On dev, Jev and the LLM tied on accuracy and Jev was better calibrated. On held-out the evidence setup we tuned on dev did not generalize: Jev fell to 0.32 macro-F1, below the LLM on the same input (0.42), the LLM on raw logs (0.54) and a classifier trained on dev (0.66). Jev stayed 7–8× faster and about 18× cheaper. This report shows every decision that led here, including the ones that didn't work.

How it works

Four bricks, each one traced

flowchart LR
  L[Raw Hadoop logs] --> P1[Parse + Drain3 patterns] --> O[(SereneDB otel_logs via OTLP)]
  Q[Question: why did job X fail?] --> B1
  O --> B1[1 Pattern: SQL counts, rarity, job facts]
  B1 --> B2[2 Evidence: rank + numbers to words]
  B2 --> B3[3 Verdict: one Jev request]
  B3 --> B4[4 Finding: answer, confidence, badge, citation]
BrickToolWhat it doesTime
IngestPython, Drain3, OTLPParse lines, glue stack traces, mask variable parts (IDs, IPs, numbers) so lines collapse into templates. 115,455 dev lines became 245 patterns.once
1 PatternSereneDB SQLFor the job in the question: its patterns with counts, containers affected, first time seen, how many of the 35 jobs share each pattern, job duration~15 ms
2 EvidencePythonPick and rank up to 12 items; turn numbers into words Jev reads well: "rare: seen in 3 of 35 jobs", "early in the job", "3.1× longer than a typical job"~0 ms
3 VerdictJevOne request, two questions in parallel: which of 4 classes, and which evidence item proves it (evidence inside the choices)~230 ms
4 FindingPythonAnswer card: class, computed confidence, "auto" or "needs review" badge, cited log pattern~0 ms

Every step writes its full input and output to a traces table. A Streamlit dashboard shows each question's path through the bricks next to every baseline's exact prompt and reply.

Chronology

What we tried, in order

  1. Setup

    Learned the tools, then made them talk to each other

    Pulled the full Jev and SereneDB docs into the repo. Found that SereneDB can call Jev straight from SQL (ai_system_one) and accepts OpenTelemetry logs natively. Measured Jev from SQL: 9 log templates × 4 questions in 313 ms.

  2. Setup

    Tested which Jev techniques sharpen answers

    • worked Evidence inside the choices: picked the root-cause log template at 0.92 confidence in 457 ms
    • worked Many questions in one request: 1 → 11 questions added only ~30 ms
    • worked Structured yes/no definitions with examples: gap between "yes" and "no" probabilities grew from 0.49 to 0.84
    • fine Option order and repeats were already stable
  3. Experiment design

    Split the data so the held-out set contains new situations

    55 jobs grouped by cluster run and application. Dev: 35 jobs, 105 questions. Held-out: 20 jobs, 80 questions, including PageRank + network disconnection and PageRank + disk full (never in dev), 11 new templates, and one question wording never used in dev. The split script moved the held-out files away and printed only counts.

  4. Run 1

    First results: Jev beat the LLM, but everything was weak

    Best Jev variant (A2) reached macro-F1 0.48 vs 0.38 for the LLM (before the fairness fixes below; the fair mirrored number is 0.48 vs 0.34). But accuracy was only 40%. The confusion table showed the reason: 37 of 60 machine-down questions were answered "normal".

    • worked Class definitions with "covers / does not cover": macro-F1 0.41 → 0.48
    • didn't More evidence fields alone (A1): no gain over A0
    • didn't Three shuffled option orders (A3): no gain, double the cost. Cut.
  5. Debugging

    Traced one wrong answer to its evidence

    A machine-down job's evidence was two lines: one ERROR and one common WARN. Of its 2,735 log lines, the WARN-or-worse filter kept 4. On that evidence, "normal 0.62" was a reasonable judgment. The problem was the evidence step, not the model.

  6. Fairness audit

    Checked whether we were making the LLM's job harder

    We were. Jev received full class definitions (definition, what it covers, what it doesn't); the LLM only got one line each. Fixed it, stored the exact LLM prompt in every trace, and re-ran. The LLM did not improve (macro-F1 0.38 → 0.35). On the walkthrough example it still answered "normal" at 0.95, three times out of three.

  7. Engineering

    Fixed what the runs exposed

    • LLM calls had no timeout and hung for 10 minutes: added a 60 s timeout and 2 retries
    • Failed calls are recorded as errors and never cached
    • Shuffle seeds used Python's per-run hash(): switched to a stable hash so reruns are identical
    • Hadoop timestamps have no timezone: pinned to UTC
  8. Diagnosis

    Looked for the missing signal in dev data

    Rare INFO-level patterns turned out to be strongly tied to failures, and failed jobs ran much longer:

    INFO pattern (was filtered out)JobsMachine down
    TaskAttempt killed because it ran on unusable node …888%
    Cannot assign container … NodeId …683%
    Releasing unassigned and invalid container …3100%

    Median job duration: normal 7.6 min, network disconnection 12.7, disk full 20.0, machine down 27.5. Labels were used only for this diagnosis, never by the pipeline.

  9. Fairness

    Made every comparison mirrored

    Until here, variants A0–A3 had only been measured on Jev, and the LLM only saw the frozen variant's evidence. The goal is a fair comparison, not a Jev win, so every variant now runs on both models with identical evidence, identical class options and the same shuffled orders. The dashboard shows both models' exact inputs side by side with an automatic identical-input check, and variants are frozen by the average score of both models.

  10. Amendment A4

    Changed the evidence step, kept everything else

    Evidence now means "unusual for this job": patterns seen in at most 25% of jobs at any severity, plus all WARN-or-worse, ranked rarest first; and the job's duration compared with the typical job. Generic, label-free, no Hadoop rules.

    • worked Jev macro-F1 0.48 → 0.51, Brier 1.01 → 0.84
    • worked The LLM gained even more: 0.34 → 0.49 (fair mirrored run, A2 → A4). The evidence step matters most for both.
    • mixed Rare INFO lines also bring noise: "lack of space for maps" (scheduler slots) made Jev say "disk full" on one example
  11. Amendment 3 · confidence

    Looked for any signal that makes "auto" answers safe

    Re-scored the existing answers of both models offline with seven confidence signals: computed confidence, top probability, top-two margin, citation confidence, answer/citation consistency, shuffle agreement and agreement across question wordings. None reaches 90% accuracy at any coverage, for either model. Jev ranks its own answers better (its most confident third is 54% right vs 37%).

    The cause is in the data: 5 jobs labelled machine down or disk full show no trace of the fault in their logs. Both models answer "normal" on all 15 of their questions, with high confidence. On that evidence, "normal" is the honest reading. Decision: keep the current confidence and re-test on GAIA.

  12. Held-out · run once

    Tested the frozen setup on 20 unseen jobs

    Frozen setup A4, identical input for Jev and the LLM (verified 80/80), plus the raw-logs LLM, the rules and a classifier trained on all dev jobs. Claude never saw the held-out data; the script printed aggregates only.

    • didn't hold Jev 0.51 → 0.32 macro-F1; LLM on the same input 0.49 → 0.42
    • surprise LLM on raw logs 0.38 → 0.54, classifier 0.48 → 0.66
    • reading our evidence selection was tuned on dev and seems to discard information on new data; the held-out set also has situations dev never had, and only 20 jobs
    • split flaw found afterwards: held-out was 100% PageRank while dev was 71% WordCount, and the duration comparison ignored job type (normal PageRank jobs run about 4.9 min vs 13.1 for WordCount). Failing PageRank jobs could look "shorter than typical", which reads like "normal".

Glossary

Every label in this report

TermMeaning
A0–A4Variants, each run on both Jev and the LLM with identical input. Each changes one thing: A0 minimal evidence and label names; A1 adds timing, rarity and an example line; A2 adds structured class definitions; A3 adds shuffled option orders; A4 switches evidence to rarity-first at any severity, plus duration vs typical
B1–B4Baselines. B1 the LLM on Jev's exact evidence for each variant; B2 the LLM on raw log lines; B3 a TF-IDF + logistic regression classifier on pattern counts; B4 hand-written keyword rules
AblationChange one component at a time and measure its effect
Template / patternA log line with its variable parts masked, e.g. Container complete event for unknown container id <ID>. Mined with Drain3
RarityIn how many jobs a pattern appears. Rare patterns carry more information (the idea behind inverse document frequency)
Macro-F1F1 computed for each class and averaged equally. Used because classes are imbalanced: machine down is 57% of dev
Brier scoreSquared error between predicted probabilities and the truth. 0 is perfect, 2 is confidently wrong. Rewards being right and honest about uncertainty
ECEExpected calibration error: when a system says 80%, how far is it from being right 80% of the time
Selective accuracyAccuracy on the questions answered automatically, above a confidence threshold
95% CIBootstrap interval: the metric recomputed on 1,000 resamples of the questions
Stratified / leave-one-run-out CVTwo ways to test the classifier: folds that keep class balance, or holding out a whole cluster run it never trained on

Full explanations, formulas and references (Drain, Loghub, Brier, ECE, selective prediction, LLM verbalized confidence, option-order bias) are in docs/PIPELINE.md.

Next

What we take into experiment 002 (GAIA)

  • Stratify the split by job type or service and compare each job with its own kind (per-service baselines), not with the whole corpus.
  • Choose evidence settings with grouped cross-validation on dev, not one dev score; the single-score choice overfit here.
  • Explore Jev's question design beyond two fixed questions: an explicit "can't tell" option, fault-or-not first, symptom-level yes/no questions, a judgment per evidence item, graded scores, a broader generic fault taxonomy, choosing the culprit service from data, and several wordings averaged. Every design is mirrored for the LLM.
  • Compare evidence selection against raw logs early. On new data the raw-logs LLM beat our selected evidence, so selection must prove it keeps the useful information.
  • Keep the trained classifier as an honest reference. It was the strongest system on held-out, though it needs labelled data from the same environment.
  • Add cross-job and time-window evidence (what other jobs and services saw at the same time), and use GAIA's service-level fault labels.
  • Re-test "auto" answers (H4) once evidence and labels line up.
